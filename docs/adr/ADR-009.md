# ADR-009: Default `ValidationPipe` Options & Normalized HTTP 400 Error Format

- **Status:** Accepted
- **Date:** 2026-11-20
- **Related:** [ADR-004](./ADR-004.md), [ADR-005](./ADR-005.md), [ADR-008](./ADR-008.md), [ADR-010](./ADR-010.md)

## Context

`class-validator` and `class-transformer` have permissive defaults that create security and correctness hazards if left unconfigured: unknown/extra fields pass through silently (mass-assignment risk), non-object payloads bypass validation if `forbidUnknownValues` is false, implicit type conversion silently coerces `"false"` to `true`, and raw `ValidationError` trees echo sensitive user inputs (like passwords) in `target` and `value`.

## Decision

### 1. Secure Default `ValidationPipeOptions`

`@bunest/validation`'s `new ValidationPipe(options?)` MUST use the following conservative defaults:

| Option                                      | Default             | Rationale                                                                                                                                                                                            |
| ------------------------------------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `whitelist`                                 | `true`              | Strips properties that have no `class-validator` decorator (prevents mass assignment).                                                                                                               |
| `forbidNonWhitelisted`                      | `true`              | Rejects payloads containing unexpected properties with HTTP 400 instead of silently dropping them (configurable to `false`).                                                                         |
| `forbidUnknownValues`                       | `true`              | Prevents non-object or decorator-less unknown payloads from passing validation as empty valid objects.                                                                                               |
| `transform`                                 | `true`              | Runs `plainToInstance(metatype, value, transformOptions)` so the handler receives an actual DTO class instance (methods, getters, `instanceof`).                                                     |
| `transformOptions.enableImplicitConversion` | `false`             | **Explicit transform policy.** Never silently coerces `"false"` -> `true` or `"42"` -> `42`. Developers MUST use explicit `@Type(() => Number)` or built-in pipes (`ParseIntPipe`, `ParseBoolPipe`). |
| `stopAtFirstError`                          | `false`             | Returns all constraint violations in one response for better API client DX (configurable to `true`).                                                                                                 |
| `skipMissingProperties`                     | `false`             | Missing required fields fail validation unless decorated with `@IsOptional()`.                                                                                                                       |
| `skipNullProperties`                        | `false`             | `null` fails validation unless permitted.                                                                                                                                                            |
| `skipUndefinedProperties`                   | `false`             | `undefined` fails validation unless decorated with `@IsOptional()`.                                                                                                                                  |
| `validationError.target`                    | `false`             | Omits full DTO object from `ValidationError` (prevents echoing secrets/passwords).                                                                                                                   |
| `validationError.value`                     | `false`             | Omits raw rejected input value from `ValidationError` (prevents echoing secrets/PII).                                                                                                                |
| `errorHttpStatusCode`                       | `400`               | Throws `BadRequestException` (configurable, e.g., `422`).                                                                                                                                            |
| `groups`                                    | `undefined`         | Optional `class-validator` validation groups.                                                                                                                                                        |
| `always`                                    | `undefined`         | Optional `class-validator` `always` flag.                                                                                                                                                            |
| `exceptionFactory`                          | Built-in normalizer | Customizable `(errors: ValidationError[]) => unknown` hook.                                                                                                                                          |

### 2. Prototype Pollution & Malformed Input Guards

1. Before running `plainToInstance`, `ValidationPipe` MUST sanitize/reject dangerous own keys (`"__proto__"`, `"constructor"`, `"prototype"`) when present as payload properties (`Object.hasOwn`), preventing prototype pollution attacks.
2. When `@Body()` receives malformed JSON, parameter extraction throws `BadRequestException("Invalid JSON payload")` (HTTP 400) before `ValidationPipe` runs—never leaking a raw `SyntaxError` as HTTP 500.
3. If `value` for a `@Body()` DTO is `null`, `undefined`, or a non-object primitive (when a DTO class metatype is expected), `ValidationPipe` MUST reject it with HTTP 400 rather than passing a primitive to `plainToInstance`.

### 3. Normalized HTTP 400 Validation Error JSON Format

All Bunest HTTP exceptions follow a single consistent JSON envelope. On validation failure, `ValidationPipe` throws a `BadRequestException` (or configured status exception) whose JSON response body MUST conform to:

```ts
export interface ValidationErrorDetail {
  field: string; // dot/bracket path: "email", "address.zipCode", "items[0].sku"
  constraints: Record<string, string>; // class-validator constraint key -> message
  messages: string[]; // Object.values(constraints), deterministic order
}

export interface ValidationErrorResponse {
  statusCode: number; // 400 (or configured errorHttpStatusCode)
  error: string; // HTTP reason phrase: "Bad Request"
  message: string; // Summary message: "Validation failed"
  details: ValidationErrorDetail[]; // Non-empty flattened list of field violations
  timestamp?: string; // ISO-8601 UTC timestamp (added by DefaultExceptionFilter)
  path?: string; // Request pathname (added by DefaultExceptionFilter)
}
```

#### Example Normalized Response (`HTTP 400 Bad Request`)

```json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "details": [
    {
      "field": "email",
      "constraints": {
        "isEmail": "email must be an email"
      },
      "messages": ["email must be an email"]
    },
    {
      "field": "address.zipCode",
      "constraints": {
        "isString": "zipCode must be a string"
      },
      "messages": ["zipCode must be a string"]
    },
    {
      "field": "items[0].quantity",
      "constraints": {
        "min": "quantity must not be less than 1"
      },
      "messages": ["quantity must not be less than 1"]
    },
    {
      "field": "unexpectedField",
      "constraints": {
        "whitelistValidation": "property unexpectedField should not exist"
      },
      "messages": ["property unexpectedField should not exist"]
    }
  ],
  "timestamp": "2026-11-20T03:00:00.000Z",
  "path": "/users"
}
```

#### Flattening Rules for Nested & Array Errors

- Recursively walk `ValidationError.children`:
  - Nested object property: `${parent}.${child.property}` (e.g., `address.zipCode`).
  - Array element index (numeric `child.property` when parent is an array): `${parent}[${child.property}]` and `${parent}[${child.property}].${grandchild.property}` (e.g., `items[0].quantity`).
- Emit an entry in `details` for every node that has non-empty `constraints`.
- `ValidationPipe` MUST NOT return raw `class-validator` `ValidationError` instances directly to HTTP clients.

### 4. Non-Validation `HttpException` Alignment

Standard `HttpException` responses from `@bunest/common` share the exact same base envelope (`statusCode`, `error`, `message`, optional `details`, plus `timestamp`/`path` added by `DefaultExceptionFilter`), ensuring uniform client-side error parsing across 400/401/403/404/405/409/422/429/500 responses.

## Consequences

- **Positive:** Secure-by-default mass-assignment and prototype-pollution protection; no silent boolean/number coercion bugs; deterministic machine-readable `details` array for frontend form binding; no accidental secret echoing.
- **Negative:** Existing loose payloads with extra properties will receive 400 unless callers configure `forbidNonWhitelisted: false`, and query DTOs require explicit `@Type(() => Number)` for numeric fields.
- **Mitigation:** Document options clearly in quickstart and allow per-route or global override via `new ValidationPipe({ ... })` or `exceptionFactory`.
