# ADR-007: Module-Scoped Providers, Export Visibility, Re-Exports, Dynamic & Global Modules

- **Status:** Accepted
- **Date:** 2026-11-20
- **Related:** [ADR-002](./ADR-002.md), [ADR-006](./ADR-006.md), [ADR-012](./ADR-012.md)

## Context

A NestJS-style modular DI container requires unambiguous rules for provider encapsulation, export visibility, transitive re-exports, dynamic modules, global modules, token collision resolution, circular dependencies, and lifecycle ordering. Without a concrete contract, `@bunest/core` cannot guarantee deterministic resolution or clear bootstrap diagnostics.

## Decision

### 1. Module Metadata & Provider Forms

```ts
export interface ModuleMetadata {
  imports?: Array<
    Type<any> | DynamicModule | Promise<DynamicModule> | ForwardReference
  >;
  controllers?: Type<any>[];
  providers?: Provider[];
  exports?: Array<
    | DynamicModule
    | Promise<DynamicModule>
    | Type<any>
    | Provider
    | string
    | symbol
    | ForwardReference
  >;
}

export interface DynamicModule extends ModuleMetadata {
  module: Type<any>;
  global?: boolean;
}
```

Supported `Provider` forms in `providers`:

- **Class shorthand:** `UsersService` (equivalent to `{ provide: UsersService, useClass: UsersService }`)
- **`ClassProvider`:** `{ provide: token, useClass: ImplClass, scope?: Scope }`
- **`ValueProvider`:** `{ provide: token, useValue: constantOrInstance }` (always singleton)
- **`FactoryProvider`:** `{ provide: token, useFactory: (...deps) => T | Promise<T>, inject?: Array<InjectionToken | OptionalFactoryDependency>, scope?: Scope }`
- **`ExistingProvider`:** `{ provide: aliasToken, useExisting: targetToken }` (aliases to a token visible in the same module)

### 2. Encapsulation & Export Visibility Rules

1. **Private by default:** Every provider declared in Module `M.providers` is visible ONLY inside `M` (to `M`'s providers, controllers, and module-bound middleware/enhancers).
2. **Explicit exports:** Module `B` importing Module `A` can inject token `T` from `A` **if and only if** `A` lists `T` in `A.exports`.
3. **Export forms:**
   - **Token export:** Exporting `T` (`Type | string | symbol`) exposes `T` if `T` is declared in `M.providers` OR exported by a module in `M.imports`. Otherwise bootstrap MUST fail fast (`InvalidExportException`).
   - **Provider object export:** Listing a `Provider` object in `exports` exports its `provide` token (and registers it in `M` if not already in `M.providers`).
   - **Module re-export:** Listing an imported module `A` (static or `DynamicModule`) in `M.exports` re-exports **all** tokens exported by `A` transitively to any module importing `M`. Re-exporting a module NOT present in `M.imports` MUST fail fast at bootstrap.
4. **No implicit transitive leaking:** If `C` imports `B` and `B` imports `A` (without `B` re-exporting `A` or `A`'s tokens), `C` CANNOT inject `A`'s providers.

### 3. Module Deduplication & Dynamic Modules

1. **Static module deduplication:** Static `@Module()` classes are deduplicated by class identity across the entire module graph. Importing `DatabaseModule` in both `UsersModule` and `OrdersModule` resolves to **one** module instance, so singleton providers inside `DatabaseModule` are shared.
2. **Dynamic modules:**
   - Returned by static factory methods (e.g., `ConfigModule.forRoot(opts)`, `CacheModule.registerAsync(opts)`), sync or `Promise<DynamicModule>`.
   - Each distinct `DynamicModule` return object creates a distinct module registration keyed by `(dynamicModule.module, registrationId)` so multiple `forFeature(...)` / named instances do not overwrite each other.
   - Reusing the exact same `DynamicModule` reference across imports deduplicates to one module registration.
   - `DynamicModule.global = true` has the same visibility effect as decorating the module class with `@Global()`.

### 4. Global Modules (`@Global()`)

1. Decorating a module with `@Global()` (or returning `{ global: true }` from a `DynamicModule`) makes its **`exports`** visible to every module in the application once imported anywhere in the module graph (convention: root `AppModule`).
2. **Non-exported providers of a `@Global()` module remain private** to that global module.
3. Importing a `@Global()` module only registers it globally; unused `@Global()` classes that are never imported in the graph are not loaded.

### 5. Token Resolution Precedence & Ambiguity

When resolving token `T` inside Module `M`, the container checks in strict order:

1. **`M`'s own local `providers`** (local provider always shadows imported or global providers of the same token).
2. **`exports` of `M`'s direct `imports`** (including transitive re-exports). If two distinct imported modules export the same token `T` and `M` does not locally override `T`, bootstrap MUST fail fast (`AmbiguousProviderException`) listing the conflicting modules.
3. **`exports` of `@Global()` modules.** If two distinct global modules export the same token `T` and neither (1) nor (2) resolves `T`, bootstrap MUST fail fast (`AmbiguousProviderException`).
4. **Missing token:** If `@Optional()` is present on the constructor parameter (or `{ token, optional: true }` in `FactoryProvider.inject`), resolve to `undefined`. Otherwise fail fast at bootstrap (`UnknownDependencyException`) reporting: requesting class, parameter index, missing token name, and owning module name.

### 6. Circular Dependencies & `forwardRef()`

- **Unwrapped circular module imports (`A -> B -> A`):** Fail fast at bootstrap with full module cycle chain. Allowed ONLY when at least one side uses `forwardRef(() => TargetModule)`.
- **Unwrapped circular provider dependencies (`SvcA -> SvcB -> SvcA`):** Detected via DFS during DI graph validation; MUST fail fast at bootstrap with exact cycle chain (`SvcA -> SvcB -> SvcA`).
- **`@Inject(forwardRef(() => SvcB))`:** Permitted for singleton class providers via deferred reference resolution (after instance allocation) with documented limitations: circular `useFactory` invocations or constructor bodies eagerly invoking methods on the uninitialized circular peer remain invalid and fail fast.

### 7. Deterministic Bootstrap & Shutdown Lifecycle Order

Module graph is topologically sorted (dependencies before dependents):

1. **Bootstrap (bottom-up topological order):**
   1. Validate full module graph, exports, token visibility, cycles, and scope leaks ([ADR-012](./ADR-012.md)).
   2. Instantiate singleton providers (awaiting async `useFactory`) and singleton controllers.
   3. Call `await instance.onModuleInit()` for all implementing providers/controllers/modules.
   4. Call `await instance.onApplicationBootstrap()` across all modules (before `Bun.serve()` starts accepting traffic).
2. **Graceful shutdown (reverse topological order — dependents before dependencies):**
   1. Stop accepting new HTTP connections (`server.stop()`).
   2. Call `await instance.onModuleDestroy()`.
   3. Call `await instance.beforeApplicationShutdown(signal)`.
   4. Call `await instance.onApplicationShutdown(signal)`.

## Consequences

- **Positive:** Predictable encapsulation matching NestJS mental model; zero silent token collisions; fail-fast bootstrap diagnostics; deterministic async resource startup/teardown.
- **Negative:** Ambiguous duplicate exports fail fast instead of silently picking "last import wins," requiring explicit local aliases or disambiguated tokens.
- **Mitigation:** Clear error messages name both conflicting modules and the colliding token.
