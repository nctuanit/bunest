# ADR-012: Request-Scoped DI Propagation & Scope-Leak Detection

- **Status:** Accepted
- **Date:** 2026-11-20
- **Related:** [ADR-001](./ADR-001.md), [ADR-003](./ADR-003.md), [ADR-007](./ADR-007.md), [ADR-008](./ADR-008.md)

## Context

Most backend services are stateless singletons, but real-world applications sometimes require per-request state (tenant context, correlation IDs, per-request audit metadata, or transaction handles). In NestJS, injecting a `Scope.REQUEST` provider into a singleton silently "bubbles" request scope up the entire dependency tree—often unintentionally destroying singleton caching and degrading throughput without developer awareness. Conversely, allowing a singleton to retain a reference to a request-scoped instance causes severe cross-request data leaks.

## Decision

### 1. DI Scope Definitions (`Scope` enum in `@bunest/common`)

| Scope | Lifetime | Instantiation Timing | Shared Across Requests? |
|---|---|---|---|
| `Scope.SINGLETON` *(default)* | Application lifetime (per module registration) | Eager at bootstrap | Yes — MUST be stateless |
| `Scope.TRANSIENT` | Per injection point / resolution call | On each resolve (at bootstrap when injected into a singleton; per request when injected into a request-scoped consumer) | Only if owned by a singleton |
| `Scope.REQUEST` | Single HTTP request lifetime | Lazy per request inside `RequestContainer` | **Never** — isolated per request, shared within the same request |

### 2. Propagation via `AsyncLocalStorage` + `RequestContainer`

1. **Runtime primitive:** Request context propagates across async boundaries using `AsyncLocalStorage<RequestContext>` from `node:async_hooks` (verified natively supported across `await` boundaries in Bun 1.4.3).
2. **`RequestContainer`:** Each request needing request-scoped DI owns an isolated `RequestContainer` (`Map<InjectionToken, unknown>`):
   - Pre-seeded with the built-in `REQUEST` injection token (resolving to the current native `Request`) and `REQUEST_CONTEXT` token (resolving to `RequestContext`).
   - Within a single request, resolving a `Scope.REQUEST` provider multiple times (e.g., via two services sharing the same request) returns the **same** instance from that request's `RequestContainer`.
   - Concurrent requests always have distinct `RequestContainer` instances—zero cross-request leakage.
3. **Zero-overhead fast path for pure-singleton routes:**
   - At bootstrap, the Execution Plan Compiler statically computes `requiresRequestScope: boolean` for every compiled route by inspecting its controller, guards, pipes, interceptors, and exception filters.
   - If `requiresRequestScope === false`: all instances are resolved once at bootstrap and bound into the route closure. No `RequestContainer` is created per request.
   - If `requiresRequestScope === true`: the route enters `requestContextStorage.run(ctx, ...)` and resolves request-scoped providers/controller/enhancers through `ctx.container`.

### 3. Strict Fail-Fast Scope-Leak Detection (Bootstrap Gate)

**Core Invariant:** A `Scope.SINGLETON` consumer MUST NEVER depend (directly or transitively) on a `Scope.REQUEST` provider.

Unlike NestJS's silent scope bubbling, Bunest enforces **explicit scope declaration and fails fast at bootstrap**:

| Consumer Scope | Injects `SINGLETON` | Injects `TRANSIENT` | Injects `REQUEST` |
|---|---|---|---|
| `Scope.SINGLETON` | Allowed | Allowed *(dedicated instance created at bootstrap)* | **FAIL FAST (`ScopeLeakException`)** |
| `Scope.TRANSIENT` | Allowed | Allowed | Allowed **only** if every enclosing consumer of this transient is `Scope.REQUEST` (otherwise **FAIL FAST**) |
| `Scope.REQUEST` | Allowed | Allowed *(dedicated instance per request)* | Allowed *(shared within same request)* |

- **Scope-leak validation runs at bootstrap** for all providers, controllers, guards, pipes, interceptors, exception filters, and module middleware before `Bun.serve()` starts.
- **Diagnostic format:** `ScopeLeakException` MUST print the exact offending dependency chain and remediation hint:
  ```text
  ScopeLeakException: SINGLETON "UsersController" cannot depend on REQUEST-scoped "TenantContext".
  Chain: UsersController [SINGLETON] -> UsersService [SINGLETON] -> TenantContext [REQUEST]
  Fix: Mark "UsersController" and "UsersService" with { scope: Scope.REQUEST }, or read ambient RequestContext inside request handlers.
  ```

### 4. Request-Scoped Lifecycle & Resource Cleanup

1. `Scope.REQUEST` providers are NOT instantiated at bootstrap and do NOT trigger `onModuleInit` or `onApplicationBootstrap`.
2. After the HTTP pipeline completes (or throws, or the client aborts via `request.signal`), the `RequestContainer` runs cleanup in a `finally` block:
   - Invokes optional `onRequestDestroy?()` (or `Symbol.asyncDispose` / `Symbol.dispose` if implemented) in reverse instantiation order.
   - Clears the internal map so request-scoped instances are immediately eligible for garbage collection.

### 5. Phased Implementation Alignment

Consistent with Section 14.2 and Section 16.3 of the implementation plan:
- `@bunest/core`'s DI graph enforces `Scope` metadata and **bootstrap scope-leak detection from Day 1** (even before full request-scoped HTTP apps are rolled out), preventing accidental scope leaks and avoiding a later DI container rewrite.
- Singleton + Transient resolution are the primary fast-path foundation; `RequestContainer` + `AsyncLocalStorage` propagation wire cleanly into the same `Injector` abstraction.

## Consequences

- **Positive:** Zero silent performance regressions from accidental NestJS-style scope bubbling; zero cross-request data leaks; zero DI overhead on pure-singleton routes; safe async propagation via Bun's native `AsyncLocalStorage`.
- **Negative:** Developers opting into `Scope.REQUEST` must explicitly annotate all intermediate consumers along the dependency chain (or use ambient `RequestContext`).
- **Mitigation:** Fail-fast bootstrap error lists the exact chain of classes to annotate, making fixes mechanical and explicit.
