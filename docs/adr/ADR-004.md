# ADR-004: Parameter Decorators Replacing `static parameters`

- **Status:** Accepted
- **Date:** 2026-11-20
- **Related:** [RFC-001](../rfcs/RFC-001-controller-routing.md), [ADR-002](./ADR-002.md), [ADR-005](./ADR-005.md), [ADR-008](./ADR-008.md)

## Context

Declaring endpoint inputs via a static array (`static parameters = [...]`) duplicates parameter order out-of-band, drifts easily during refactoring, and diverges from NestJS ergonomics. With legacy decorators adopted in [ADR-002](./ADR-002.md), TypeScript natively supports parameter decorators with exact `parameterIndex` and `design:paramtypes` reflection.

## Decision

1. **Legacy parameter decorators are the primary input-binding API.** `static parameters = [...]` is NOT required and is NOT part of the public API.
2. **Supported built-in parameter decorators (`@bunest/common`, re-exported by `@bunest/core`):**
   | Decorator                          | `ParameterSource` | Extracts                                                                                            |
   | ---------------------------------- | ----------------- | --------------------------------------------------------------------------------------------------- |
   | `@Body(property?, ...pipes)`       | `"body"`          | Parsed request body (or `body[property]`), cached once per request                                  |
   | `@Query(property?, ...pipes)`      | `"query"`         | Query string map (or single/array value for `property`)                                             |
   | `@Param(property?, ...pipes)`      | `"param"`         | Route params map (or `params[property]`)                                                            |
   | `@Headers(property?, ...pipes)`    | `"header"`        | Lowercased headers object (or `headers.get(property.toLowerCase())`)                                |
   | `@Cookies(property?, ...pipes)`    | `"cookies"`       | Parsed request cookies (via Bun native `req.cookies` `CookieMap` or `Cookie` header fallback)       |
   | `@Req()`                           | `"request"`       | Native Web `Request` (with `params` when matched)                                                   |
   | `@Res()`                           | `"response"`      | Mutable `ResponseContext` builder (`status`, `headers`, `cookie()`, `clearCookie()`)                |
   | `@Ip()`                            | `"ip"`            | Resolved client IP (via `server.requestIP(req)?.address`, respecting configured trust-proxy policy) |
   | `@HostParam(property?, ...pipes)`  | `"hostParam"`     | Matched host parameter(s) for host-constrained controllers                                          |
   | `@UploadedFile(field?, ...pipes)`  | `"uploadedFile"`  | Single `UploadedFileInfo` from `multipart/form-data`                                                |
   | `@UploadedFiles(field?, ...pipes)` | `"uploadedFiles"` | `UploadedFileInfo[]` from `multipart/form-data`                                                     |
   | `createParamDecorator(factory)`    | `"custom"`        | User-defined extractor `(data, ctx: ExecutionContext) => value`                                     |
3. **Index-based metadata contract:**
   - Every decorator records `{ index, source, key?, pipes?, factory?, data? }` keyed by `parameterIndex` on `(prototype, handlerKey)`.
   - Bunest NEVER parses JS parameter names from `Function.prototype.toString()`.
   - Parameters may appear in any order (including sparse/undecorated slots, which receive `undefined`).
   - Decorating the same `(handlerKey, index)` with two conflicting parameter decorators MUST fail fast at bootstrap.
4. **Single-read body caching:**
   - Because Web `Request.body` is a single-use `ReadableStream`, `@bunest/http` parses the body lazily on first `@Body()` / `@UploadedFile()` access and caches the parsed value (and parse error, if malformed) inside `RequestContext`.
   - Multiple `@Body("email")` and `@Body("name")` parameters on the same handler read from the cache and MUST NOT throw `Body already used`.
   - Content-type handling: `application/json` (and `+json`) -> `req.json()` (malformed JSON -> `400 Bad Request`); `application/x-www-form-urlencoded` -> key-value record; `multipart/form-data` -> `req.formData()` split into fields and `UploadedFileInfo`; `text/*` -> `req.text()`.
5. **Missing vs `null` vs empty string:**
   - Missing query/header/body keys remain `undefined`; JSON `null` remains `null`; empty query `?a=` remains `""`.
6. **No implicit primitive coercion:**
   - Query, path param, header, and cookie values arrive as `string` (or `string[]` for repeated query params).
   - Bunest MUST NOT implicitly run `Boolean(val)` (which turns `"false"` into `true`) or `Number(val)`. Developers use explicit built-in pipes (`ParseIntPipe`, `ParseFloatPipe`, `ParseBoolPipe`, `ParseUUIDPipe`, `ParseArrayPipe`, `ParseEnumPipe`, `DefaultValuePipe`) or `ValidationPipe` with explicit `@Type(...)`.

## Consequences

- **Positive:** Co-located, refactor-safe parameter declarations; full NestJS DX; deterministic minification-safe argument resolution; zero duplicate body reads.
- **Negative:** Requires compiling parameter extractors + `design:paramtypes` at bootstrap; TypeScript interfaces/unions cannot supply runtime `metatype`.
- **Mitigation:** Compile parameter extraction plans once at bootstrap ([RFC-001](../rfcs/RFC-001-controller-routing.md)) and document explicit pipe/DTO requirements.
