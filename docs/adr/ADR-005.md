# ADR-005: `class-validator` + `class-transformer` as Default DTO Validation

- **Status:** Superseded by [ADR-015](./ADR-015.md) (Bun-native `@bunest/class-validator` & `@bunest/class-transformer` replace third-party defaults while preserving the `PipeTransform` seam and upstream coexistence)
- **Date:** 2026-11-20
- **Related:** [ADR-002](./ADR-002.md), [ADR-004](./ADR-004.md), [ADR-008](./ADR-008.md), [ADR-009](./ADR-009.md), [ADR-015](./ADR-015.md)

## Context

DTO validation is a cornerstone of NestJS-style backend development. Writing a bespoke validation library in Bunest would create long-term maintenance drag, while choosing an incompatible schema-only default would break the primary class-based DTO ergonomics (`@IsEmail()`, `@IsString()`, `@ValidateNested()`) expected with legacy decorators.

## Decision

1. **`class-validator` + `class-transformer` is the default DTO validation stack**, integrated via `ValidationPipe` in `@bunest/validation`.
2. **Opt-in execution via pipes (not mandatory on every endpoint):**
   - Validation decorators (`@IsEmail()`, `@MinLength()`, etc.) register metadata only—they do NOT validate requests unless a `ValidationPipe` is bound (globally via `app.useGlobalPipes(new ValidationPipe())`, or at controller/method/parameter level via `@UsePipes` / `@Body(new ValidationPipe())`).
   - Endpoints without DTOs or without `ValidationPipe` pay zero validation overhead.
3. **Metatype resolution & skip rules:**
   - `ValidationPipe` inspects `ArgumentMetadata.metatype` (populated from `design:paramtypes` at bootstrap).
   - Validation is skipped when `metatype` is `undefined` or is a built-in non-DTO constructor: `String`, `Boolean`, `Number`, `Array`, `Object`, `Function`, `Symbol`, `BigInt`, `Date`, `RegExp`, `Request`, `Response`.
4. **Transform + Validate lifecycle:**
   - Convert plain payload into a DTO instance via `plainToInstance(metatype, value, transformOptions)` when `transform: true`.
   - Run `await validate(instance, validatorOptions)` (always `await` so async custom validators work reliably).
   - On validation failure, throw a normalized `BadRequestException` (400, or configured `errorHttpStatusCode`)—never leaking raw `class-validator` `ValidationError[]` internals directly (see [ADR-009](./ADR-009.md)).
   - On success, pass the transformed DTO instance into the controller handler (when `transform: true`).
5. **Extensible via `PipeTransform`:** Because validation runs strictly through the standard `PipeTransform` interface, alternative schema validators (Zod, Valibot, TypeBox) can be integrated as drop-in pipes without modifying `@bunest/core` or `@bunest/http`.

## Required Test Coverage (`@bunest/validation`)

The integration suite MUST verify: nested DTOs (`@ValidateNested` + `@Type`), DTO arrays, optional/nullable fields, validation `groups`, async custom validators (`@ValidatorConstraint({ async: true })`), DTO class inheritance, `whitelist` / `forbidNonWhitelisted` / `forbidUnknownValues`, and prototype pollution (`__proto__` / `constructor` keys).

## Consequences

- **Positive:** Mature validation rule ecosystem; idiomatic NestJS DTO DX; zero need to maintain a custom validator library; clean `PipeTransform` seam for future schema adapters.
- **Negative:** `class-transformer` implicit conversions can be surprising if misconfigured; requires legacy decorators and explicit `@Type()` for nested/array DTOs.
- **Mitigation:** Lock strict, secure `ValidationPipe` defaults with explicit transform policy in [ADR-009](./ADR-009.md).
