# ADR-008: Exact HTTP Execution Pipeline Order & Precedence Rules

- **Status:** Accepted
- **Date:** 2026-11-20
- **Related:** [RFC-001](../rfcs/RFC-001-controller-routing.md), [ADR-004](./ADR-004.md), [ADR-009](./ADR-009.md), [ADR-010](./ADR-010.md), [ADR-011](./ADR-011.md), [ADR-012](./ADR-012.md)

## Context

The implementation plan (Section 5 and Section 16.1) highlights that the exact ordering between middleware, guards, interceptors, parameter extraction, pipes, handler execution, response serialization, and exception filters—along with global/controller/method/parameter precedence—must be locked by specification and integration tests. Ambiguity here causes subtle bugs in auth, logging, validation, and error handling.

## Decision

### 1. Canonical 11-Stage HTTP Execution Pipeline

Every matched HTTP request executes through the following exact sequence:

```text
Incoming Request
  1. Route Match (Bun.serve native routes OR fallback dispatcher -> 404/405)
  2. RequestContext Init (+ AsyncLocalStorage / RequestContainer if scoped)
  ── Exception Filter Boundary begins ──────────────────────────────────────────
  3. Security / CORS Pre-Processing (preflight short-circuit, payload limits, trust-proxy IP)
  4. Middleware (Global -> Module-bound matching path/method)
  5. Guards (Global -> Controller -> Method)
  6. Interceptors [Before] (Global -> Controller -> Method)   ──┐
  7. Parameter Extraction (by ascending ParameterMetadata.index) │ Onion wrapped
  8. Pipes & Validation (Global -> Controller -> Method -> Param)│ by CallHandler
  9. Controller Handler (await controller[handlerKey](...args))  │ .handle()
 10. Interceptors [After] (Method -> Controller -> Global)    ──┘
 11. Response Serialization (ADR-010 + CORS/cookies/headers merge)
  ── Exception Filter Boundary catches throws from stages 3–11 (and 404/405) ──
  -> Exception Filters (Method -> Controller -> Global -> DefaultExceptionFilter)
  -> Native Web Response (with CORS headers preserved)
```

### 2. Stage-by-Stage Normative Behavior

1. **RequestContext Init:** Allocates per-request `RequestContext` holding raw `Request`, matched `params`, lazy parsed-body cache, mutable `ResponseContext` (status, headers, cookies), and `ExecutionContext`. Runs inside `AsyncLocalStorage.run(...)` when request-scoped DI or ambient context is required ([ADR-012](./ADR-012.md)).
2. **Security / CORS:**
   - If CORS is enabled and the request is a CORS preflight (`OPTIONS` + `Origin` + `Access-Control-Request-Method`), short-circuits with `204 No Content` and configured `Access-Control-*` headers.
   - Enforces configured max body size (`bodyLimit`) before full body buffering -> throws `PayloadTooLargeException` (413).
   - Ensures configured CORS headers are attached to **both** normal responses and Exception Filter error responses.
3. **Middleware (`BunestMiddleware`):**
   - Signature: `use(req: Request, res: ResponseContext, next: () => Promise<Response | void>): Promise<Response | void> | Response | void` (class implementing `BunestMiddleware` or plain function).
   - Configured globally via `app.use(...)` or per-module via `configure(consumer: MiddlewareConsumer)` with `.apply(...).exclude(...).forRoutes(...)`.
   - Middleware chains execute sequentially; returning a `Response` short-circuits downstream stages (skipping guards/interceptors/handler) while still applying CORS headers; throwing routes to Exception Filters.
   - Because Bun native routes bypass `fetch()`, matching middleware lists are **pre-resolved at bootstrap** and bound directly into each compiled route closure ([ADR-011](./ADR-011.md)).
4. **Guards (`CanActivate`):**
   - Signature: `canActivate(context: ExecutionContext): boolean | Promise<boolean>`.
   - Executed sequentially. First guard returning `false` throws `ForbiddenException` (403). Throwing an explicit `HttpException` (e.g., `UnauthorizedException` 401) propagates that exception directly.
   - Guards run **before** interceptors and **before** body parsing/pipes so unauthorized requests never pay body-parse or validation costs.
5. **Interceptors (`BunestInterceptor` — Promise Onion Model):**
   - Bunest core uses a **native Promise-based `CallHandler`** with **zero mandatory RxJS dependency**:
     ```ts
     export interface CallHandler<T = unknown> {
       handle(): Promise<T>;
     }
     export interface BunestInterceptor<T = unknown, R = unknown> {
       intercept(context: ExecutionContext, next: CallHandler<T>): Promise<R> | R;
     }
     ```
   - Outer interceptors wrap inner interceptors (`Global -> Controller -> Method` on entry; `Method -> Controller -> Global` on exit).
   - `next.handle()` invokes the next interceptor, or at the innermost layer executes **Stages 7 -> 8 -> 9** (Parameter Extraction -> Pipes -> Handler) and returns the handler's resolved value.
   - An interceptor MAY short-circuit without calling `next.handle()` (e.g., cache hit), transform the return value after `await next.handle()`, or `try/catch` errors thrown by stages 7–9.
6. **Parameter Extraction:**
   - Extracts raw parameter values in ascending `ParameterMetadata.index` order (`@Param`, `@Query`, `@Body` via single-read cache, `@Headers`, `@Cookies`, `@Req`, `@Res`, `@Ip`, `@HostParam`, `@UploadedFile(s)`, custom param decorators).
   - Malformed JSON/multipart body throws `BadRequestException` (400) here before pipes execute.
7. **Pipes & Validation (`PipeTransform`):**
   - For each parameter (in ascending index order), executes its pipe chain sequentially: output of pipe `i` becomes `value` input of pipe `i + 1`.
   - Skips running global/controller/method validation pipes on `@Req()` and `@Res()` raw framework objects (`ArgumentMetadata.type === "custom"` unless explicitly opted in).
   - Any pipe throwing an error aborts remaining parameters and prevents the handler from being invoked.
8. **Controller Handler:**
   - Invoked with `await controllerInstance[handlerKey](...resolvedArgs)`.
9. **Response Serialization:**
   - Serializes the final return value (after all interceptors unwind) into a native Web `Response` per [ADR-010](./ADR-010.md).
10. **Exception Filters (`ExceptionFilter`):**
    - Catches any error thrown in stages 3–11 as well as fallback 404/405 exceptions.
    - Matches filters decorated with `@Catch(...exceptionTypes)` using `error instanceof ExceptionType`. Empty `@Catch()` matches any error at its scope level.
    - First matching filter in precedence order handles the error and returns a `Response` (or writes via `ResponseContext`).
    - **Built-in `DefaultExceptionFilter`** (lowest precedence fallback):
      - `HttpException` -> serializes normalized error JSON with `exception.getStatus()` and any exception headers (e.g., `Allow` on 405).
      - Unknown / non-`HttpException` error -> logs internally via `Logger` and returns `500 Internal Server Error` with safe message (`"Internal server error"`). **MUST NOT leak stack traces or internal messages when `NODE_ENV === "production"`.**

### 3. Precedence Rules Matrix

| Mechanism | Execution Order | Short-Circuit / Override Semantics |
|---|---|---|
| **Middleware** | Global -> Module (topological order, registration order) | Returning `Response` or throwing stops pipeline |
| **Guards** | Global -> Controller -> Method | All must pass; first `false` (403) or throw stops pipeline |
| **Interceptors (before)** | Global -> Controller -> Method | Outer wraps inner; skipping `next.handle()` bypasses handler |
| **Pipes** | Global -> Controller -> Method -> Parameter | Chained per parameter (`v0 -> p1 -> p2 -> ... -> vn`) |
| **Interceptors (after)** | Method -> Controller -> Global | Inner transforms/observes result before outer |
| **Exception Filters** | **Method -> Controller -> Global -> Default** | **Most-specific first**; first `@Catch(...)` match wins |

### 4. DI-Aware Enhancers

Enhancers registered via class tokens (`@UseGuards(AuthGuard)`, `APP_GUARD`, `APP_PIPE`, `APP_INTERCEPTOR`, `APP_FILTER`) are resolved through the owning module's DI container at bootstrap (or per-request if request-scoped per [ADR-012](./ADR-012.md)). Pre-instantiated enhancers (`@UsePipes(new ValidationPipe())`, `app.useGlobalPipes(...)`) are used directly as singletons.

## Consequences

- **Positive:** Eliminates pipeline ordering ambiguity; aligns with NestJS mental model while dropping RxJS overhead from core; guarantees unauthorized requests never parse/validate bodies and error responses retain CORS headers.
- **Negative:** NestJS interceptors using RxJS `Observable.pipe()` require a thin adapter rather than running unmodified.
- **Mitigation:** Document the Promise-based `CallHandler` cleanly; an optional RxJS adapter package can wrap Promises if community demand arises later.
